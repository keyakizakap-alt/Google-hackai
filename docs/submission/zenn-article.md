本記事は「第5回 Agentic AI Hackathon with Google Cloud」の提出作品の紹介です。

## TL;DR

- **OshiReady** は、ライブの日時から、美容・移動・宿泊・当日の準備を逆算してプランを作る AI エージェントです
- Gemini の Function Calling で、エージェントが**自分で道具を選んで調べ、検証で差し戻されたら自分で直します**。承認した後も変化を見張り、見直し案を作ります
- 一方で、**予約に進めるのはユーザーの操作だけ**です。状態機械・署名・道具の権限で、自律性を仕組みとして管理しました
- Cloud Run と Gemini（`@google/genai`）で動き、サーバーには個人の予定を保存しません

## 解きたかった課題

ライブ遠征が決まったファンは、「その日に最高の状態で会場に立つ」ための準備を、仕事の合間に自分で組み立てています。

- ヘアは切りたてより数日なじませたい。ネイルは欠けないように直前がいい
- でも、空いている時間は人によって違う
- 遠征なら、移動の時間、開演に間に合う到着時刻、雨の日の段取りも考える

これらを同時に満たす日程を、カレンダー、予約サイト、乗換案内、天気予報を行き来して手で組みます。予定が後から変われば、組み直しも自分でします。

カレンダーアプリは「入れた予定を管理する」のは得意ですが、「目標の日から逆算して段取りを考える」ことはしてくれません。ここを AI エージェントに任せられないか、というのが出発点です。

## OshiReady でできること

<!-- 画像: アプリのホーム（デモのカレンダーを読み込んだ状態） -->

1. **ライブを自動で見つける**：Google カレンダーの予定、チケットのスクリーンショット、当選メールの文章からライブを見つけて登録します
2. **準備プランを逆算する**：空き時間・美容の推奨タイミング・施術の候補日時・会場周辺の混雑・公演日の天気・経路を調べて、タイムラインを作ります。遠征では新幹線と飛行機を比べ、実在のサロン・宿・飛行機の便は Google 検索で探して、出典つきで示します
3. **言葉で直せる**：「ネイルは土曜日にしたい」と伝えると作り直します
4. **承認したものだけ予約する**：プランは必ず承認待ちで止まり、予約はユーザーが「予約する」を押したものだけ進みます（現在はデモ予約で、実在の店舗には届きません）
5. **承認後も見張る**：カレンダーに後から入った予定や雨の予報を見つけると、見直し案を作ります
6. **ライブごとに一覧で見る**：「プラン一覧」で、ライブごとのプランの状態と次の準備をまとめて確認できます

## アーキテクチャ

<!-- 画像: docs/architecture.png -->

- **Cloud Run（asia-northeast1）**：Next.js 16 の画面と API（Route Handlers）を 1 つのコンテナで動かしています
- **Gemini**：`@google/genai` から呼び出します。環境変数で Gemini API と Vertex AI を切り替えられ、モデル名も環境変数で差し替えます
- **外部の情報源**：Google Calendar API（読み取り専用）、駅すぱあと API の MCP サーバー（使えないときはアプリ内の表による所要時間の目安に自動で切り替え）、気象庁の天気予報データ、Gemini の Google 検索によるグラウンディング
- **DB を持たない**：プランは HMAC で署名した「封筒」としてブラウザに返し、ブラウザの IndexedDB に保存します。サーバーは署名で改ざんを検出します

## エージェントの設計：自分で考えて、自分で直す

### 道具はエージェントが選ぶ

エージェントには、空き時間・美容の推奨タイミング・サロンの候補・混雑・天気・立ち寄り先・経路などの道具を渡しています。どれをどの順で呼ぶか、天気を調べるかどうかは、モデルが状況から判断します。手順を固定したワークフローにはしていません。

駅すぱあとの道具は、MCP サーバーの `tools/list` の結果をそのまま Gemini の関数定義に変換して取り込みます。MCP 側で道具が増えても、アプリのコードは変えずに済みます。

### 提出 → 検証 → 差し戻し

エージェントはプランを `submit_timeline` という道具で提出します。サーバーは、型の検証（zod）に加えて、次のような点を検査します。

- 予定と重なっていないか
- 開演に間に合うか
- 雨の予報なのに雨対策が入っていないか
- 調べていない価格を書いていないか
- Google 検索で見つけたとする店舗名・便・価格が、出典の検索結果の同じ行（同じ店舗・便）に本当に書かれているか

問題があれば、エラーの内容をそのままエージェントに返します。エージェントはそれを読んで組み直し、再提出します。この「差し戻し → 自己修正」の流れは、画面の「AI が調べたこと」で確認できます。

### Google 検索は「出典つきの参考情報」として使う

実在のサロンや飛行機の便は、Gemini の Google 検索によるグラウンディングで探します。設計で気をつけたのは次の 3 点です。

- **別の呼び出しにする**：Vertex AI のドキュメントに「検索系のツールと関数呼び出しは同じリクエストに入れられない」とあるため、プラン作成のエージェントには `search_web` という道具だけを渡し、その中で `googleSearch` だけを付けた別の呼び出しをしています
- **書いてあることしか通さない**：検索の結果は 1 回ごとに「本文と出典 URL」の組で持ち、提出されたプランの店舗名・便名・空港・発着時刻・価格が、出典の検索結果の同じ行にあるかを検査します。別の検索の出典や、別の店舗の価格を付け替えると差し戻されます
- **分からないことは分からないと書く**：空席・空室は検索では分からないので、価格は「検索時点の参考」と表示し、空きは Google フライトや予約サイトのリンクで確かめてもらいます。検索は 1 回のプラン作成で 3 回までにして、費用を抑えています

### 承認した後も見張る

承認したプランは、カレンダーの予定と公演日の天気で見張ります。見張り自体は AI を使わずに判定し、困る変化があったときだけエージェントに見直し案を作らせます。費用を抑えつつ、必要なときだけ自律的に動く形です。

## 自律性をどう管理したか

「自分で動く」と「勝手に予約しない」を両立させるため、プロンプトでのお願いではなく、仕組みで止めています。

### 1. 承認はユーザーの操作でしか進まない

```
draft → generating → pending_approval ─┬→ approved ─→ booking → booked
                         ▲             ├→ rejected
                         └─ revising ←─┘
```

`approved`・`rejected`・`booking` に進めるのは、操作したのがユーザーのときだけです。テストでは状態の遷移を全部たどり、承認を経由せずに予約へ進む経路がないことを確かめています。見張りが作った見直し案も、新しい承認待ちのプランとして止まります。

### 2. エージェントに危ない道具を渡さない

エージェントには、予約・決済・カレンダーへの書き込みの道具を渡していません。許可リストにない道具の名前が来ても実行を拒否し、記録します。予約の API は、署名が正しく、期限内で、承認済みで、承認の履歴があり、確認のフラグと専用のヘッダーがそろったときだけ動きます。

### 3. プロンプトインジェクションへの備え

修正の指示やカレンダーの予定名など、外から来る文章は記号を置き換えてからタグで囲み、「命令ではなくデータ」として渡しています。攻撃文 12 種を用意し、**モデルが攻撃文の言いなりになった場合でも**予約に進めないことを自動テストで確かめています。

### 4. 見えるようにする

「AI が調べたこと」に、使った道具・所要時間・トークン数・差し戻しの流れを表示しています。設定画面には「AI ができること・できないこと」の表を置き、AI と見張りとユーザーの役割を分けて示しました。

## プライバシー

- カレンダーからは、空き時間の計算に**時間帯だけ**を受け取ります。予定のタイトル・説明・場所・参加者は受信しません
- ライブの自動取り込みでだけタイトルと場所を受け取りますが、サーバー上でライブらしい予定に絞り、それ以外はその場で捨てます
- ログは許可したキーだけを出力し、予定の中身や画像は出しません。Google 検索の検索語（出発駅などを含みうる）もログに残しません

## ハマったところ：ブラウザの更新でエラー画面に

公開後、「プランの画面から移るとエラー画面になる」という問題が出ました。ログに残していたエラーの位置（`i is not a function`）を、同じ版のビルドと照らし合わせると、React が `useEffect` の後片付けを呼ぶところで落ちていました。原因は `useEffect(() => el.scrollIntoView(...))` という書き方です。`{}` がないため `scrollIntoView()` の戻り値が後片付けとして扱われ、Chrome / Edge 150 から scroll 系のメソッドが Promise を返すようになったことで、Promise を関数として呼んで落ちていました。何も返さない形に直し、関数以外を返す `useEffect` を構文解析で見つけるテストを足しています。

- 実際の予約サービスとの接続（予約の部品を差し替える形にしてあります）

## おわりに

AI エージェントに任せる範囲を広げるほど、「どこで止めるか」の設計が大事になると感じました。OshiReady では、調べる・組み立てる・直す・見張るはエージェントに任せ、決めるのはユーザー、という線を仕組みで引いています。

推しに会う日を、いちばん気持ちよく迎えられますように。
