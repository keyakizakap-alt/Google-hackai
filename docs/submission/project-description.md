## OshiReady — 推しに会う日を、いちばん気持ちよく

推しに会う日は、最高の状態で会場に立ちたい。

**課題**：ライブが決まったファンは、美容の最適な時期（ヘアは2〜5日前、ネイルは1〜3日前）・仕事や学校の合間の空き時間・遠征の移動と宿を同時に満たす日程を、カレンダー・予約サイト・乗換案内・天気予報を行き来して手で組んでいます。予定が変われば組み直しも自分。カレンダーアプリは「入れた予定の管理」はできても、「目標の日からの逆算」はできません。

**解決**：OshiReady は、ライブの日時から準備を逆算する AI エージェントです。カレンダーやチケットのスクショからライブを見つけ、Gemini の Function Calling で空き時間・美容の最適日・混雑・天気（雨ならヘアセットや持ち物も調整）・経路（駅すぱあと MCP。遠征は新幹線と飛行機を比較）を、どれをどの順で使うかも自分で決めて調べ、Google 検索で実在のサロン・宿・便と参考価格を出典つきで提案します。「ネイルは土曜に」と言葉で直せ、承認後もカレンダーと天気の変化を見張って見直し案を作り、前日のリマインドまで寄り添います。プランはライブごとの一覧でまとめて管理できます。

**魅力（自律と安心の両立）**：検証で差し戻されたプランは自分で直して再提出します。一方、予約に進めるのは利用者の承認と操作だけで、AI に予約・決済の道具は渡さず、攻撃文 12 種で乗っ取られても予約に届かないことをテストしています。出典に裏付けのない店名・価格は差し戻し、「AI が調べたこと」で判断の過程を見せます。予定の中身はサーバーに保存せず、Cloud Run と Gemini で動きます。

## 詳細版（参考・800 字を超える）

### OshiReady — 推しに会う日を、いちばん気持ちよく迎える

### 対象ユーザーと課題

ライブやコンサートに遠征するファン（推し活をする人）が対象です。

ライブの日が決まると、ファンは「その日に最高の状態で会場に立つ」ための準備を、仕事や学校の合間に自分で組み立てています。

- **美容には最適なタイミングがある**：ヘアは数日なじませたいので 2〜5 日前、ネイルは欠けないように 1〜3 日前など
- **空いている時間は人によって違う**：仕事・学校・ほかの予定の合間を探す必要がある
- **遠征には移動・宿泊・当日の段取りがある**：開演の何分前に会場に着くか、雨ならどうするか

この 3 つを同時に満たす日程を、カレンダー・予約サイト・乗換案内・天気予報を何度も行き来して手で組んでいます。予定が後から変わると、組み直しもすべて自分で行います。スケジュール管理アプリは「入れた予定を管理する」ことはできても、「目標の日から逆算して、準備の段取りを自分で考えて提案する」ことはできません。

### ソリューション

OshiReady は、ライブの日時から逆算して、美容・移動・宿泊・当日の準備のプランを作る AI エージェントです。

1. **ライブを自動で見つける**：Google カレンダーを連携すると、予定からライブを見つけて登録します。チケットのスクリーンショットや当選メールの文章からも読み取れます
2. **エージェントが自分で調べて逆算する**：Gemini の Function Calling で、空き時間・美容の推奨タイミング・施術の候補日時・会場周辺の混雑・公演日の天気・経路（駅すぱあと MCP。使えないときは所要時間の目安に自動で切り替え。遠征では新幹線と飛行機を比べる）、Google 検索での実在のサロン・宿・飛行機の便と価格の目安を、必要なものだけ自分で選んで調べ、準備のタイムラインを組み立てます
3. **人が承認するまで予約しない**：プランは必ず「承認待ち」で止まります。予約は、ユーザーが内容を確認して承認し、「予約する」を押したものだけ進みます
4. **承認した後も見張る**：カレンダーに後から入った予定や公演日の天気を見張り、困ることが見つかればエージェントが見直し案を作ります。見直し案も承認待ちで止まり、今のプランや予約は勝手に変えません
5. **当日まで寄り添う**：前日・直前のリマインド（アプリ内通知とカレンダー用ファイル）を端末の中だけで作ります
6. **ライブごとにまとめて見られる**：「プラン一覧」で、登録したライブごとの準備プランの状態（承認待ち・承認済み・予約済み）と次の準備を一覧にし、そこから確認・承認・予約に進めます

### 特徴（審査基準との対応）

**① 課題の新規性と解決策の有効性**
「美容の最適タイミング × 自分の空き時間 × 遠征の移動」を同時に満たす逆算は、これまでファンが手作業でしていた部分です。目標の日（ライブ）から逆算して準備全体を組み立て、変化があれば組み直しまで提案します。

**② 自律性・エージェントらしさ（と、その管理）**
- どの道具をどの順で使うか、天気や立ち寄り先を調べるかどうか、遠征で新幹線と飛行機のどちらにするかは、モデルが状況から判断します（固定の手順にしていません）
- 実在のサロン・宿・飛行機の便は、Gemini の Google 検索によるグラウンディングで探します。検索結果に書かれていない店舗名・便・価格は検査で差し戻し、その出典のページが裏付けている記述（同じ店舗・便の行）に書かれているものだけを、出典つき・「検索時点の参考価格」として表示します
- サーバー側で提出されたプランを検証し、開演に間に合わない・予定と重なる・雨対策が抜けている、といった問題があれば差し戻します。エージェントは差し戻しを読んで自分で組み直します
- 承認後も見張りを続け、変化に応じて自分から見直し案を作ります
- 自律性は仕組みで管理しています。状態機械で「承認」「予約」に進めるのはユーザーの操作だけで、エージェントには予約・決済・カレンダー書き込みの道具を渡していません。プランは署名付きで改ざんを検出します
- 「AI が調べたこと」に、使った道具・所要時間・トークン数・差し戻しと再提出の流れを表示し、判断の過程を見えるようにしています
- 攻撃文 12 種を使い、モデルが乗っ取られた場合でも予約に進めないことを自動テストで確かめています

**③ 実装品質と拡張性**
- Next.js 16 を Cloud Run（asia-northeast1）で動かし、Gemini は `@google/genai` から呼び出します（Vertex AI 経由に切り替え可能）
- サーバーに個人データを保存しない設計です。カレンダーは時間帯だけを受け取り、予定のタイトルや参加者は受信しません
- カレンダー・予約・経路の連携は部品化していて、モックを実際のサービスに差し替えられます。駅すぱあと MCP のツールは実行時に取り込むため、ツールが増えてもコードの変更は不要です
- 自動テスト（Vitest）と CI（GitHub Actions）、検査を通った版だけを公開する Cloud Build の手順、実際の Gemini で完成率・自己修正率・攻撃への耐性・費用を測る評価の仕組みがあります
<!-- - 評価の結果（N 回）：完成率 __%、自己修正率 __%、攻撃文 12 種への耐性 __/12、1 プランあたりの費用 約 __ 円 -->
- 使っていないときは止まる設定（最小インスタンス 0）にでき、AI の呼び出し回数に 1 日の上限を設けて費用を抑えています。Google 検索の呼び出しは 1 回のプラン作成で 3 回までにし、設定 1 つで止められます
- Google 検索はプラン作成の AI とは別の呼び出しで使い、検索語はログに残しません。Google の検索候補（Search Suggestions）は利用条件に従って表示します

### 使用技術

Cloud Run / Gemini（Gemini API・Vertex AI、Function Calling・構造化出力・Google 検索によるグラウンディング）/ Cloud Build / Artifact Registry / Secret Manager / Cloud Logging / Google Calendar API / 駅すぱあと API MCP（使えないときは所要時間の目安に自動で切り替え）/ 気象庁の天気予報データ / Next.js 16・React 19・TypeScript・Tailwind CSS v4

### 補足

- 予約は**デモ予約**で、実在の店舗・交通機関・宿には届きません（画面に明記しています）。サロン・宿・便の空き（空席・空室）は取得していません。店舗・便と価格は Google 検索で見つけた参考情報で、検索結果に書かれたものだけを出典つきで表示します。それ以外の、エージェントの自律ループ・検証と差し戻し・承認の仕組み・見張り・カレンダー連携・天気・経路は実際に動きます
- デモに出てくるアーティスト名はすべて架空です
- どこを開発し、どこがモックかは、リポジトリの README「開発した範囲とモックの箇所」に記載しています
