# 審査期間の運用（〜2026 年 12 月 1 日。余裕をみて 12 月 2 日まで）

提出した状態を保ったまま、審査員がいつ開いても動くようにするための手順。
すべて Cloud Shell で実行する（`export OSHIREADY_PROJECT_ID='your-project-id'` を先に実行）。

## 期間中に止まる・壊れる可能性があるもの

| 項目 | 何が起きるか | 対策 |
|---|---|---|
| デモのカレンダーのライブの日付 | 日付が過ぎると「これからのライブ」から消える | 12/2 より後の日付のライブを入れておく（下の 1）。すべて過去になっても、アプリ内蔵の架空のライブで補う（自動） |
| 止まった状態からの起動 | 最初に開いたとき数秒待たされる | 期間中は `judging` モードで常に 1 台起動しておく（下の 2） |
| 提出後の変更 | main へのマージで内容が変わる・壊れる | 期間中は main にマージしない。提出したリビジョンを控えておく（下の 3） |
| 費用・請求先 | 請求先アカウントが止まると、アプリも止まる | 予算アラートを設定し、支払い方法・無料トライアルの期限を確認しておく（下の 4） |
| Google ログインでの連携 | 同意画面が「テスト」のままだと、7 日で連携が切れる | 審査員には「デモのカレンダーで試す」を使ってもらう（サービスアカウントで読むため期限なし） |
| 駅すぱあと | キーの期限切れ・障害時は経路を検索できない | 自動で「経路の目安」に切り替わり、プラン作成は止まらない |
| AI のモデル | 提供が終わると AI のプランが作れない | `gemini-3.5-flash` は、Gemini API の非推奨ページで「終了日は未発表」（2026-10-10 時点。Vertex AI 側は未確認）。期間中に週 1 回の点検で確認する |

## 1. デモのカレンダーにライブを入れる（提出前に 1 回）

審査員がいつ開いても「これからのライブ」があるように、12 月以降の日付で数件入れる。準備（美容院など）の逆算ができるよう、開く日から 2 週間以上先のものが 1 件以上あるとよい。

| タイトル | 場所 | 日時の例 |
|---|---|---|
| IVE WORLD TOUR 京セラドーム大阪 | 京セラドーム大阪 | 2026-12-19 18:00〜21:00 |
| SEVENTEEN ライブ 東京ドーム | 東京ドーム | 2027-01-16 17:00〜20:00 |
| Mrs. GREEN APPLE 公演 | 日本武道館 | 2027-02-13 18:00〜21:00 |

11 月中の日付のライブも 1 件あると、11 月前半に開いた人にも直前の準備の例を見せられる。
すべて過去になった場合は、アプリが内蔵の架空のライブ（今日から約 1〜3 か月後）を代わりに表示する（ログに `sample.no_upcoming_live` が出る）。

## 2. 審査期間用の設定に切り替える

```bash
bash scripts/cloud-run-demo-mode.sh judging   # 提出したらすぐ（12/2 までの目印が付く）
bash scripts/cloud-run-demo-mode.sh status    # いまの設定と期限を確認
```

- 常に 1 台起動・最大 3 台・1 台あたり同時 20 件・AI は 1 日 300 回（1 台あたり）。
- 終了日を変えるときは `OSHIREADY_JUDGING_UNTIL=2026-12-03 bash scripts/cloud-run-demo-mode.sh judging`。
- 費用の目安（**概算・未確認**）：待機中の 1 台（1 vCPU・1 GiB）は、公式の料金表の Tier 1 の待機単価（vCPU・GiB とも 1 秒あたり $0.0000025）で計算すると 1 日あたり約 $0.43、30 日で約 $13。東京リージョンの単価は料金表で確認する（https://cloud.google.com/run/pricing ）。これに実際の利用分と Gemini の利用料が加わる。

## 3. 提出した状態を保つ

```bash
# 提出したコミットに目印を付ける（ローカルで。GitHub に残る）
git tag submission-2026 <提出したコミット> && git push origin submission-2026

# いま動いているリビジョン名を控える
gcloud run services describe oshiready --region=asia-northeast1 --format='value(status.latestReadyRevisionName)'
```

- 期間中は main にマージしない（Dependabot の提案 PR も、期間が終わるまで置いておく）。
- 万一、変更して壊れたときは、控えたリビジョンに戻す：

```bash
gcloud run services update-traffic oshiready --region=asia-northeast1 --to-revisions=<控えたリビジョン名>=100
```

  戻したあと `judging` などで設定を変える前に、`--to-latest` で最新に向け直すこと（向け直さないと、新しい設定が使われない）。

## 4. 期間中の点検（週 1 回・5 分）

```bash
bash scripts/cloud-run-doctor.sh               # 設定とヘルスチェック
bash scripts/cloud-run-demo-mode.sh status     # 常に 1 台・期限の確認
```

- スマホで公開 URL を開き、「デモのカレンダーで試す」→ ライブが並ぶ → プランを作る、まで通す。
- Google Cloud の「お支払い」で、今月の費用と予算アラートの状態を確認する。

## 5. 期間が終わったら（12/3 以降）

```bash
bash scripts/cloud-run-demo-mode.sh lite   # 使っていないときは止まる設定に戻す（目印も外れる）
```

- Dependabot の PR や、期間中に控えていた変更をマージしてよい。
- 公開をやめる場合は、デモのカレンダーの共有からサービスアカウントを外す（`docs/demo-calendar.md`）。
